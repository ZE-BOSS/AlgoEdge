# §0 Profit target — fixed, and why the last fix did not hold

You reported it twice. The first time I fixed a real defect that was not the
cause, so this time I traced the whole path against **your saved config** rather
than reasoning about it. Three defects, stacked. **Each one breaks the target on
its own, and two of them act before the breaker is ever consulted — which is
exactly why adopting unknown groups did not help.**

### Your config, as saved

```
account risk:   target_profit_enabled = False        <- off at the account
Crash 1000 Index / DriftJumpAlpha_v1 slot override:
                target_profit_enabled = True
                profit_target_scopes  = 'TRADE'
                profit_target_basis   = 'FLOATING'
                profit_target_action  = 'CLOSE_AND_PAUSE'
                (no amount on the slot — the $50 lives on RiskParams as the default)
```

### Defect 1 — the amount never reached live

`build_live_risk_config` was a hand-written dict literal. Measured: it carried
**71 of 93 `RiskParams` fields**, and the 22 it dropped included the entire
profit-target mechanism:

```
max_trade_profit        <- THE $50
max_monthly_profit
profit_target_scopes
profit_target_basis
profit_target_action
profit_target_is_pct
accounting_utc_offset_hours   <- so the WAT boundary never reached live either
```

The switch (`target_profit_enabled`) was in the literal, so the slot could arm
the target and the breaker would agree it was armed — while
`ProfitTargetPolicy.amounts` had no `TRADE` key at all. `_check_trade` then
returns `None` on its first line, for "no per-trade amount set at all". Silent,
and indistinguishable from "no target configured".

### Defect 2 — the slot was skipped before any of that mattered

`_apply_profit_targets` read `slot_book.config_for(slot.slot_id)`. That method
falls back to the **account** config for a slot it has never been told about:

```python
def config_for(self, key): return self.slot_configs.get(key) or self.base_config
```

`slot_configs` is only populated by `_slot_engine`, which is called from **deep
inside the signal-execution branch** of the scan loop (`bot_service.py:1322`) —
after a signal exists and has passed its gates. So a slot that is **holding an
open position and producing no new signal** — precisely when a profit target
matters — read the *account's* `target_profit_enabled`, found `False`, and hit
`continue`. The breaker was never consulted, the groups were never adopted, and
nothing was logged.

I reproduced both states directly:

```
STATE A  slot never registered -> config_for returns the ACCOUNT base
         target_profit_enabled = False   -> SKIPS THE SLOT: True
STATE B  slot registered       -> target_profit_enabled = True
         max_trade_profit      = None    -> still inert (defect 1)
```

### Defect 3 — the one I fixed last time

`active_groups` is never rehydrated, so a position surviving a restart was
dropped. That fix was correct and stays. It just sat behind the other two.

### The fix

1. **`build_live_risk_config` now derives its base from the dataclass**
   (`_every_risk_field`) and lets the curated entries override it. A new
   `RiskParams` field now reaches live *by existing*. Verified: **93 of 93**.
2. **`_apply_profit_targets` now resolves each slot** via
   `self._slot_engine(slot, config).circuit` instead of looking it up, so the
   fallback cannot apply.

# W1 — MT5 ↔ Journal ↔ Investors reconciliation

## 1.1 The anchor, from the Journal

```
anchor_trade   = first Trade with a real strategy_id (not MANUAL_*)
anchor_time    = 2026-09-30 02:35:06
anchor_balance = 3266.92          <- that trade's balance_before
anchor_account = <needs trades.mt5_account, see W5 #9>
```

No statements, no broker history, no admin typing. It is read from the Journal
and recomputed if the Journal changes, and the UI shows the anchor trade so the
figure is always traceable to a row you can click.

**Why `balance_before` cannot simply be summed.** Measured: the 02:35 and 02:40
trades both record `3266.92 → 3029.59`. It is a snapshot of the account at that
instant, so with overlapping positions consecutive rows double-count. The ledger
therefore uses `balance_before` **only** for the anchor, and derives everything
after it from flows:

```
expected_balance(t) = anchor_balance
                    + capital_in       - capital_out
                    + realised_profit  - realised_loss
                    - commission - swap - interest - tax
                    + adjustments
residual(t)         = actual_balance(t) - expected_balance(t)
```

`residual` is displayed **always**, including when it is `0.00`. A
reconciliation that only speaks up when it is unhappy is one you stop trusting.

> I already know this residual is non-zero today. Journal `pnl` over the bot era
> sums to `+963.41` against an anchor of `3266.92`, implying `4230.33`, while the
> last `balance_after` is `3903.11` — a **−327.22** difference that swap and
> commission are the obvious candidates for. The ledger's job is to name it, not
> to absorb it.

## 1.2 Capital flows, per account, every account real

New module `backend/mt5/history.py` — the only reader of MT5 deal history, on
the single MT5 thread (`run_mt5`), never imported by the investor package.

```python
CAPITAL_IN, CAPITAL_OUT, COST, CREDIT_NOT_CAPITAL, TRADE_RESULT, ADJUSTMENT, UNKNOWN
```

Classification is a **per-account table**, seeded from what I measured on both
terminals and editable in the admin UI — not an `if` chain:

| Deal type | Default class | Why |
|---|---|---|
| `BALANCE (2)` | `CAPITAL_IN`/`CAPITAL_OUT` by sign, or `ADJUSTMENT` if the comment matches a reset pattern | Deriv funds and resets here |
| `CHARGE (4)` | `CAPITAL_IN` where the account is configured so, else `COST` | **measured: FundedNext's entire $25,000 arrives as CHARGE** |
| `CORRECTION (5)` | `UNKNOWN` → **must be reviewed** | a broker fix; could be either |
| `CREDIT (3)`, `BONUS (6)` | `CREDIT_NOT_CAPITAL` | not withdrawable, must never back units |
| `COMMISSION (7–11)`, `INTEREST (12)`, `TAX (17)` | `COST` | **not deposits** — the current code calls them deposits |
| `DIVIDEND (15, 16)` | `TRADE_RESULT` | position income |
| `BUY/SELL_CANCELED (13, 14)` | `COST` | reversals |
| `BUY/SELL (0, 1)` | `TRADE_RESULT` | profit + commission + swap + fee |

Anything in `UNKNOWN` **blocks the reconciliation from reporting healthy** and
appears in a review queue.

**Why a table and not a rule.** Measured on your two terminals: Deriv books
capital as `BALANCE (2)`, FundedNext as `CHARGE (4)`. A `type == 2` filter —
the obvious correction to today's code — would miss FundedNext's $25,000
entirely. And both Deriv balance deals carry the *same* comment for a top-up and
a deduction, so comment text alone is not a discriminator either; sign carries
direction.

Stored once in `mt5_cash_flows`, keyed `UNIQUE(account_login, deal_ticket)` —
the same append-only idempotent shape `unit_transactions` already uses, so
re-syncing cannot double-count.

**Timezone.** `deal.time` is broker-server time. `data_fetcher.py` already
solves this (`_SERVER_OFFSET_CACHE`, `ALGOEDGE_MT5_SERVER_UTC_OFFSET`); reused
rather than re-answered. Day/week/month boundaries roll on
`RiskParams.accounting_utc_offset_hours` (WAT).

Journal does not.

- Add `trades.mt5_account` and `trade_positions.mt5_account`, stamped at write.
- Backfill: where `mt5_ticket` matches a deal in a known account's history,
  attribute it; otherwise leave `NULL` and show those rows as

- A new `mt5_accounts` table holds login, broker, server, label, the deal-class

# W3 — Multiple VPS backends, one front end

## 3.1 What exists
One seam, already there:

```js
const BACKEND_URL = localStorage.getItem('backend_url') || DEFAULT_URL;
export const setBackendUrl = (url) => { localStorage.setItem('backend_url', url); api.defaults.baseURL = `${url}/api`; }
```

One global mutable URL, one axios instance, one `useWebSocket()` reading
`getBackendUrl()`. The work is turning one slot into a registry.

## 3.2 Design (per-server tokens, Q8)
Registry in a persisted Zustand store:
```js
{ id, label, baseUrl, role: 'live'|'demo', color, token, refreshToken, user, health }
```

- **One axios instance per server**, each with the existing interceptors bound
  to *that* server's token. Not one instance whose `baseURL` is mutated — that
  breaks the moment the dashboard polls live while a backtest streams from demo.
- **Sign in per server**, with an indicator of which you are signed in to. No
  shared `SECRET_KEY`, so a demo compromise is not a live compromise.
- **Server switcher in the top bar**, the active server's colour as a persistent
  accent so you cannot misread which account you are looking at. Destructive

# W4 — Reinforcement-learning signal agent

## 4.0 How this is built (Q9)

No calendar phasing. Everything in §4.1–4.9 gets built: the env, the reward, the
trainer, the validator, the distiller, the registry, the dataset ingest, the
Agents page, Backtester integration, leak detection and the close-signal path.
Then I train agents, run the gate, and report what happened.

**The gate in §4.6 stays, enforced in code rather than in the schedule.** It is
not a delaying device — it is the thing that stops the platform from handing you
a confident false positive, which is the specific failure this codebase has been
burned by repeatedly.

**One honest constraint that is not an estimate:** training is compute-bound.
≥5 seeds × ≥8 CPCV folds × years of bars is real GPU/CPU hours per agent per
asset, and no amount of planning compresses it. I will make the queue
observable — progress, ETA, cancel — so you can see where it is, and I will
report results as they land rather than at the end.

## 4.1 What the research says

- **PPO is the most stable** algorithm in comparative trading studies;
  value-based methods are more fragile.
- **Backtest overfitting is the defining failure.** The current standard is
  *combinatorially purged cross-validation* (CPCV) with *probability of backtest
  overfitting* (PBO) and the *deflated Sharpe ratio*, and the discipline is to
  **reject** agents that fail rather than ship the best-looking one. CPCV
  measurably beats walk-forward on both PBO and DSR.
- **Seed fragility is severe.** Standing advice: if Sharpe moves by 2 across
  five seeds, you do not have a result.
- **Single-regime overfit** is the classic trap — train 2015–19, test 2020, and
  a beautifully tuned agent spikes and never recovers.
- **RL does not clearly beat supervised learning for direction.** A 2022 study
  found a supervised approach outperforming RL on crypto. RL's real edge is in
  *cost-aware sequential decisions* — holding, exiting, sizing.
- **Costs decide it.** Reported FX/crypto RL results die above roughly
  **1–4 bp**; a hybrid survived to 4 bp where plain RL managed about 1 bp.

> ### ⚠️ Why that last line matters here
> 1 bp on EURUSD is about **0.1 pip**. Your measured cost model puts FX
> slippage at 0.1 pip *plus* spread, and your own playbook study found **8 of
> 15 paired cells flip sign between Deriv and FundedNext** on the same rule and
> market. The published results sit inside a cost budget your brokers do not
> offer. On Boom/Crash it is worse: spike-side stops fill λ toward the bar
> extreme, and a naïve bar model faked **+0.46R on random entries**.
>
> That does not make this pointless — it makes **cost realism and
> out-of-sample discipline the product**, and the agent the easy part. Note that
> the one place RL is *best* supported by the literature is exactly the thing
> you just asked for: **managing an open position** (§4.8).

## 4.2 Why this fits the codebase

Your 70/30 reward split is **reward decomposition**, a published explainable-RL
technique. "State the strategy you follow" is **policy distillation into
interpretable rules**, also an active published line. And the mechanism already
exists: `BaseStrategy.gate(name, passed, detail)` + `GateRecorder` record a
named confluence per candidate and tag signals with `passed_gates`,
`gate_vector` and `confluence_tags`. An agent built as a `BaseStrategy` inherits
the explainability surface, the gate funnel and the Strategy Lab for free.

## 4.3 Risk management is a hard filter

Confirmed as you specified, and worth stating precisely because §4.8 adds a
second direction of traffic:

```
RL agent  ->  proposes:  OPEN(direction, confidence, gate_vector)
                         CLOSE(fraction, reason, gate_vector)
                         TIGHTEN_STOP(level)
RiskEngine / SlotBook / CircuitBreaker  ->  disposes
```

The agent never sizes, never sets a stop, never overrides a halt. It cannot
breach a drawdown cap, a slot brake or a concurrency limit, **because those
numbers are not in its observation at all** — not withheld by policy, absent by
construction. There is no action in its space that sets a lot size, a stop
distance or a risk percentage, so "the model has no access to money management"
is a property of the interface rather than a rule it is trusted to obey. **Opens can be refused. Closes are always honoured** — see §4.8 for
why that asymmetry is deliberate and safe.

## 4.4 Architecture

```
backend/rl/
  spec.py        AgentSpec: asset, timeframe, features, reward weights, seeds
  features.py    observation builder, reusing strategies/core (ATR, swing, bars)
  env.py         Gymnasium env wrapping the EXISTING backtester, not a new sim
  reward.py      decomposed: 0.70 money + 0.30 adherence, logged separately
  train.py       PPO (stable-baselines3), N seeds, CPCV folds, artefacts
  validate.py    PBO, deflated Sharpe, seed dispersion, regime + broker splits
  distill.py     policy -> decision tree -> named gates = the stated strategy
  registry.py    approved agents, versioned, content-hashed
  datasets.py    raw CSV/JSON ingest, provenance, in-sample fingerprint
  exit_policy.py the open-position head (§4.8)
  charter.py     StrategyCharter + CharterProposal: frozen, versioned, approved
  adherence.py   scores a decision against the APPROVED charter, live and in test
  leakguard.py   prefix-stability probe + the shuffled/shifted controls (§4.11)
backend/strategies/strategy_rl/engine.py   one BaseStrategy wrapping any agent
```

**The env wraps the existing backtester** — the single most important decision
here. A fresh simulator would not have your λ spike fills, measured per-symbol
spreads and swaps, the minimum-stop floor, next-bar-open fills, or the `BarFeed`
that gives backtest and live identical bar sequences. An agent trained against a
kinder simulator produces a number that dies on contact with the app.

## 4.5 Reward

Per closed trade, logged as **separate series, never only as a sum**:

- `money = R_net` after measured costs, with a Sortino-style downside penalty
  (the literature prefers this to raw return for risk alignment);
- `adherence = fraction of the gates in the APPROVED CHARTER that were true at
  entry` — scored against the charter you signed off (§4.10), not against
  whatever the policy currently prefers, which is what stops the agent from
  earning the adherence term by redefining its own strategy;
- **`exit_quality`** (new, §4.8): the counterfactual — what the trade would have
  returned had it run to its original stop/target — so closing early is rewarded
  only when it actually beat holding.

Weights 0.70 / 0.30 as you specified, with `exit_quality` inside the money term
so an agent cannot farm adherence by never trading. Keeping the components
separate is what makes "it made money by abandoning its strategy" visible
instead of hidden inside one scalar.

## 4.6 The gate an agent must pass to reach your Backtester

Pre-registered and enforced in code, not a judgement call afterwards:

| Test | Bar |
|---|---|
| Seeds | ≥ 5; reject if Sharpe dispersion > 1.0 |
| CPCV | ≥ 8 paths; **PBO < 20%** |
| Deflated Sharpe | positive after the multiple-testing haircut |
| Cost stress | still positive at **2× measured spread and slippage** |
| Regime split | positive in ≥ 2 of 3 independent windows |
| Broker cross-check | positive on **both** Deriv and FundedNext bars, or scoped to one and labelled |
| Adherence | ≥ 0.6 mean, else the stated strategy is fiction |
| **Exit head** | **must beat the same agent with its exit head disabled** (§4.8) |
| **Charter** | gates are executable predicates and the distilled thesis reproduces the policy's decisions on held-out bars; otherwise the charter is decoration |
| **Leak probe** | every feature prefix-stable (§4.11) |
| **Shuffled labels** | break-even minus costs — anything better means the env leaks |
| **Shifted entry** | degrades gracefully by one bar, rather than collapsing |

Failures are stored with their report and marked `REJECTED`. **Rejections are
kept** — the record of what did not work is worth more than another candidate.

## 4.7 In-sample leak detection

Every dataset gets a content hash and `(symbol, timeframe, start, end)`
coverage; every agent stores exactly what it trained on. Picking a backtest
window calls `POST /api/rl/overlap` and the UI shows 🟢 clean, 🟡 N% overlap
with the ranges named, or 🔴 fully in-sample — **and disables Run**, with "pick a
window after `<date>`". A warning you can click past is a warning that gets
clicked past.

## 4.8 NEW — the agent closes running trades

Your requirement: the agent keeps seeing the open trade's market data and, when
it reads reversal, signals a close — so profit is not given back and the stop is
not hit.

**This needs no new plumbing.** The hook already exists and is already used:

```python
def on_position_bar(self, symbol, timeframe, candles, position) -> TradeAction | None
```

- Called **once per closed bar for every open position the strategy owns**, by
  the backtester and, via `LIVE_POSITION_EXITS`, by
  `position_manager._check_strategy_position_exit`. **The same hook on both
  sides, so backtest and live agree for free** — the parity rule this project
  already depends on.
- `TradeAction` already supports `CLOSE` (with `close_pct`, so partial exits
  work) and `MODIFY_SL`.
- `OvernightSession_v1`, `TrendBreakout_v1` and `VWAP_v1` already opt in, so
  this path is exercised in production today.

**The exit head.** A second policy output sharing the entry encoder, observing
the entry features plus position state: unrealised R, bars held, MFE/MAE so far,
distance to stop and to target, and the entry gate vector. It emits
`HOLD | CLOSE_PARTIAL | CLOSE_ALL | TIGHTEN_STOP`, each with the named gates
that fired — so an exit is as explainable as an entry.

**Granularity, stated plainly:** decisions are **per closed bar, not per tick.**
`BarFeed` guarantees backtest/live parity at bar granularity and nothing
guarantees it at tick granularity. A tick-level exit would be untestable, and an
untestable exit is how you get a backtest that does not predict live. If you
want faster reactions, the answer is a lower timeframe for the exit head — which
is a config value, measurable, and parity-safe.

**Precedence, and why closes are always honoured.** A close only ever reduces
exposure, so it cannot breach a risk limit:

1. Circuit-breaker halt → flatten wins over everything.
2. Agent `CLOSE` → honoured. It can never increase risk.
3. `TIGHTEN_STOP` → honoured **only if it tightens**, never if it widens. The
   existing `MODIFY_SL` path already enforces tightening-only.
4. Stop / target / trailing / max-hold → unchanged, and still the backstop. The
   agent replaces nothing; it can only act *earlier*.
5. Agent `OPEN` → subject to every risk gate, refusable.

**How I will know whether it helps.** The §4.6 gate requires the agent with its
exit head to beat **the same agent with the head disabled**, on the same seeds
and folds. Measured against three honest baselines: no early exit, a fixed
trailing stop, and the existing per-strategy `max_hold_bars`.

> ⚠️ The specific risk to watch, and the reason for that ablation: an early-exit
> policy trained on a profitable period learns to cut winners, because cutting
> always looks good right after a drawdown in the training window. This project
> has measured break-even exits destroying real edge before — BE at 1.5R turned
> 16 of 113 BTCUSD trades into BE_SL exits the research never took, and
> trailing was measured actively harmful on several shipped strategies. The exit
> head is the single most overfit-prone component in W4, and it gets the
> strictest test for that reason.

## 4.9 NEW — the agent supervises other strategies' trades

Your requirement: a trained agent, when selected and toggled on, can monitor and
close trades **another** strategy opened — so an agent and a rule-based strategy
work in tune and the rule's win rate improves. Toggleable in backtest and live,
and testable so you can see whether it actually helps.

### Why this is a genuinely good fit

It is the one use of RL the literature actually supports. §4.1: RL does **not**
clearly beat supervised learning at calling direction, but its real edge is in
*cost-aware sequential decisions* — holding, exiting, managing. Supervision is
that job and nothing else. The agent is not second-guessing the entry; it is
answering "is this trade still working?", on a position someone else opened,
with no say in whether it was opened.

It also sidesteps the hardest part of W4. A supervisor needs no entry edge to be
worth having. It can be measured against one clean baseline — *the same
strategy, unsupervised* — which is a far sharper test than "did this agent make
money".

### The mechanism

`on_position_bar` is called per closed bar **for every open position the strategy
owns**. A supervisor must see positions it does *not* own, so one addition:

```python
# BaseStrategy
SUPERVISES_OTHER_STRATEGIES = False    # opt-in, default off
def on_foreign_position_bar(self, symbol, timeframe, candles, position, owner) -> TradeAction | None
```

- `owner` carries the opening strategy's id, its entry gate vector and its
  declared thesis, so the agent can learn *that strategy's* failure modes rather
  than treating every trade as anonymous. This is what makes "understand how
  other strategies work" concrete: `GateRecorder` already stamps
  `passed_gates`, `gate_vector` and `confluence_tags` onto every signal, and
  they are already persisted on the `Trade`. The supervisor reads them.
- Both backtesters and `position_manager` already iterate open positions per
  bar. The change is to stop filtering that iteration to the owning strategy
  when a supervisor is active — the same hook, the same loop, on both sides, so
  **backtest and live still agree for free**.
- Returns the existing `TradeAction`: `CLOSE` (with `close_pct`, so partial
  exits work) or `MODIFY_SL`. No new action type.

### Precedence — supervisors may only reduce risk

Extends §4.3 and §4.8, and the rule is the same one, which is why it is safe:

| | |
|---|---|
| 1 | Circuit-breaker halt → flatten, wins over everything |
| 2 | **The owning strategy's own exit** → wins over a supervisor. A strategy's measured rule is not overridden by an agent; the agent can only act *earlier*. |
| 3 | Supervisor `CLOSE` → honoured. Reduces exposure, so it cannot breach a limit. |
| 4 | Supervisor `MODIFY_SL` → honoured **only if it tightens**. The existing path already enforces tightening-only. |
| 5 | Supervisor opening anything, sizing anything, or widening a stop → **not expressible.** There is no action for it. |

A supervisor therefore cannot turn a winning strategy into a losing one by
trading; it can only cut trades early. That bounds the damage to exactly one
failure mode — cutting winners — which is measurable, and is what the ablation
below exists to catch.

### Toggling, as you asked

- Per agent: `supervises: [strategy_id, ...] | "ALL"`, plus the symbols it may
  supervise. An agent trained on Crash 1000 does not get to supervise GBPJPY.
- **In the Backtester:** a "Supervising agents" multi-select next to the
  strategy. The run then reports **three columns side by side** — unsupervised,
  supervised, and the difference — from the *same* bar sequence and the same
  fills, so the comparison is not two runs that drifted apart.
- **Live:** the same selection per slot, in the slot editor, defaulting off.
  Turning it on names the strategy and the agent in the confirmation.
- The supervisor's every action is logged with its gate vector and written to
  the trade's `exit_reason` as `RL_SUPERVISOR::<agent>@<version>`, so the
  Journal shows which exits were the agent's. Without that you cannot attribute
  the result afterwards.

### Reward, for a supervisor

Supervision has its own reward, because "did it make money" is the wrong
question for something that never opens a trade:

```
reward = 0.70 * saved_R  +  0.30 * adherence
saved_R = (what the trade actually returned)
        - (what it would have returned unsupervised, same bars, same fills)
```

That counterfactual is exactly what the backtester can compute, by replaying the
same group with the supervisor disabled. Cutting a winner scores **negative**;
cutting a loser before its stop scores positive. An agent that closes everything
immediately scores near zero, not well — which is the degenerate policy to guard
against.

### The bar it must clear

Added to §4.6, and it is stricter than the entry gate because the baseline is
sharper:

| Test | Bar |
|---|---|
| **Supervised vs unsupervised** | must beat the **same strategy, same seeds, same folds, same bars**, unsupervised |
| Per-strategy | must not make **any** supervised strategy worse; a supervisor that helps one and hurts another is scoped to the one |
| Winner protection | mean R of trades it closed early must be **≤** mean R of trades it let run, or it is cutting winners |
| Trade count | ≥ 100 supervised trades per strategy, or the result is not measurable |
| Cost stress | holds at 2× measured spread and slippage |

> ⚠️ **The honest risk, stated once.** An early-exit policy trained on a
> profitable period learns to cut winners, because cutting always looks good
> just after a drawdown inside the training window. This project has measured
> precisely this: break-even at 1.5R turned **16 of 113** BTCUSD trades into
> BE_SL exits the research never took, and trailing was measured *actively
> harmful* on several shipped strategies. A supervisor is a learned version of
> the same intervention, with more freedom and no pre-registered thesis — so it
> is the most overfit-prone thing in W4, and it gets the strictest test.
>
> I will build it and I will measure it. I am not going to tell you in advance
> that it will work.

## 4.10 NEW — the strategy is a charter the admin approves

Your requirement: the model may not change its strategy at will. It states the
strategy explicitly, **you approve it**, and any later change is a **proposal**
you approve or reject. That is what makes the adherence reward mean something —
a reward for "following your strategy" is worthless if the agent can rewrite the
strategy whenever following it becomes inconvenient.

### The charter

Training produces a `StrategyCharter`: a frozen, versioned, content-hashed
artefact that is the agent's declared strategy.

```
charter_id, agent_id, version, status, hash,
  thesis            one paragraph in plain language, from distill.py
  gates             [{name, plain_english, predicate, weight, hit_rate, mean_R}]
  setup_tiers       A / B / C, each a named subset of gates (your wording)
  entry_rule        which tier, which direction, which session window
  exit_rule         what the exit head is allowed to act on
  instruments       the symbols and timeframes it may trade
  supervises        which other strategies it may supervise, if any
  validation        the full §4.6 report that earned it approval
  approved_by, approved_at, superseded_by
```

`gates` and `setup_tiers` are not prose. Each gate is an **executable
predicate** over the observation, so "did it follow its strategy" is computed,
not asserted — and it is computed against the **approved** charter, never
against whatever the live policy currently prefers.

### Status, and what each one permits

| Status | Train | Backtest | Live | Adherence measured against |
|---|---|---|---|---|
| `DRAFT` | yes | no | no | — |
| `PROPOSED` | frozen | **yes, labelled "unapproved"** | no | the proposed charter |
| `APPROVED` | frozen | yes | yes | this charter |
| `SUPERSEDED` | no | historical runs only | no | itself, for reproducibility |
| `REJECTED` | no | no | no | kept with your reason |

**Nothing reaches a live slot without `APPROVED`.** Enforced where the strategy
is built, not in the UI, so an API call cannot bypass it.

### Proposing a change

The agent cannot edit an approved charter. When continued training finds
something the charter does not express — your example: a new market pattern that
works — it emits a `CharterProposal`:

```
proposal_id, from_version, to_version, kind, status
  kind      ADD_GATE | REMOVE_GATE | RETIER | WIDEN_INSTRUMENTS | CHANGE_EXIT
  diff      gate-by-gate, old vs new, in plain language
  evidence  the §4.6 report for the proposed charter AND for the approved one,
            on the same seeds and the same folds
  delta     expectancy, win rate, PBO, deflated Sharpe, max DD — both versions
  why       what the agent found, in words, from distill.py
```

Rules I will enforce:

- **One proposal open per agent.** No stacking changes you have not seen.
- **A proposal must beat the approved charter on the §4.6 gate**, measured the
  same way, or it cannot even be submitted. You should never be asked to approve
  something that has not already earned it.
- **Approving bumps the version and supersedes the old charter.** The old one is
  kept, so every historical run can still be reproduced against the charter it
  actually ran under.
- **Rejecting records your reason**, and the agent may not re-propose the same
  diff — compared by hash — without new evidence.
- While a proposal is open, **live keeps trading the approved charter.** A
  pending change changes nothing until you say so.
- Adherence during the proposal's own backtest is scored against the *proposed*
  charter; adherence live is always scored against the *approved* one.

### Drift detection — what makes this more than paperwork

An agent can quietly stop following its charter without proposing anything: the
policy drifts, adherence falls, and it keeps trading. So adherence is monitored
live, per agent, as a rolling figure:

- below the charter's own adherence floor for N consecutive trades → **the agent
  is suspended from live and you are emailed**, with the gates it has been
  skipping;
- it does not silently fall back to trading unsupervised — the slot stops taking
  the agent's signals and says why in the Journal.

That is the honest reading of "we can consistently be using the strategy and be
getting the points for following it": if the agent stops following it, that must
be visible and must stop, rather than being absorbed into a P&L number.

### In the UI

A **Charter** tab on each agent: the thesis, the gates with their hit rates and
mean R, the tiers, and the validation report that earned approval — with
**Approve** / **Reject** and a reason box. A **Proposals** queue shows any open
diff side by side, approved vs proposed, with both validation reports. Live
adherence is a chart on the same page.

## 4.11 NEW — no lookahead, and how each route is closed

You said the model must not have lookahead bias. This is the part of W4 where a
mistake is invisible and fatal: every lookahead leak makes the backtest better
and live worse, and it never announces itself. So here is each route and what
closes it.

### What the codebase already guarantees

`backend/strategies/bar_feed.py` is a real asset here. Its contract:

> At primary bar `i` the engine sees the primary bars up to `i-1` (bar `i` is
> still forming) and, for every higher timeframe, the bars that had fully closed
> by bar `i`'s open. Each timeframe is handed to the engine only when it has
> produced a NEW closed bar.

That is bar-level causality *and* correct higher-timeframe alignment — the part
most people get wrong — and `LiveBarFeed` gives live the identical call
sequence. **The RL env wraps this rather than replacing it**, so the agent
inherits the guarantee instead of needing a new one. This is the single
strongest reason not to write a fresh simulator.

### What BarFeed does not cover, and the fix for each

| Route | How it leaks | Closed by |
|---|---|---|
| **Feature scaling** | fitting a mean/σ, min-max or quantile on the whole dataset puts every future bar into every past observation | scalers fit on the **training fold only**, stored inside the agent, applied unchanged at inference. Caught by the probe below. |
| **Reward counterfactuals** | `saved_R` and `exit_quality` are computed from bars after the decision | legitimate in the **reward**, fatal in the **observation**. Structural separation: `features.py` may not import the counterfactual module, and the env passes reward and observation through separate channels. A test asserts the observation vector is identical whether or not the counterfactual is computed. |
| **CPCV folds** | a trade's label spans bars that fall in a test fold | **purge** every training observation whose label window overlaps a test fold, plus an **embargo** of max-hold bars after each test fold. Already §4.6; restated because purging without the embargo is the common half-measure. |
| **Measured per-symbol tables** | `SLOT_TP1_RR` and `SYNTH_SLOT_PARAMS` were chosen on history that includes the RL test window, so applying them makes the *environment* leak | RL evaluation runs with `use_strategy_exit_defaults=False`, and any per-symbol table used is restricted to values provably chosen before the test window. Recorded per run, so a result cannot be read without knowing which applied. |
| **HTF resampling from raw CSV** | building an H1 bar from M5 bars that include the forming one | the CSV ingest produces frames through the **same** alignment BarFeed expects, and the loader asserts every HTF bar close time is ≤ the primary bar open. |
| **Instrument selection** | picking the assets that looked good is survivorship bias in the experiment, not in the code | the asset list is pre-registered on the `AgentSpec` before training, and the report names every asset attempted, including the discarded ones. |
| **Supervisor view of a foreign trade** | reading the owning strategy's gate vector as later revised | `owner` carries the vector **as recorded at entry**, which `GateRecorder` already persists on the `Trade`. Never re-derived. |
| **Dataset overlap** | backtesting on bars the agent trained on | §4.7: content hashes, coverage ranges, Run disabled on a full overlap. |
| **Leading-NaN back-fill** | a primitive that back-fills from the first valid value borrows forward | named and banned in feature code — see the measurement below. |

### The probe — a test, not a promise

Any feature an agent is allowed to see must be **prefix-stable**: `f(bars[:i])`
must be identical regardless of what follows bar `i`. I built the probe and ran
it against this codebase's own primitives:

```
PREFIX-STABILITY PROBE  (features over 400 bars vs the first 300)
  causal  anchored VWAP line                 identical over the shared prefix
  causal  anchored VWAP sigma                identical over the shared prefix
  causal  rolling mean 20     (control)      identical over the shared prefix
  LEAKS   centred mean 20     (control)      9 of 300 differ, from 9 bars before the cut
  LEAKS   whole-series z-score (control)     300 of 300 differ
```

The two controls are there to prove the probe detects leaks rather than merely
passing everything. The session-anchored VWAP is genuinely causal, which is
worth knowing since it is the one shared feature every strategy already reads.

One real finding from the same probe: `_ffill_bfill` back-fills leading NaNs
from the first valid observation —

```
input  [nan nan nan  5.  6.  7.]
output [  5.   5.   5.  5.  6.  7.]      <- the first three take bar 3's value
```

Harmless where it is used today (it starts at a session anchor and callers read
`[-1]`), but as a feature primitive it is a three-bar lookahead. It is banned in
`features.py`, and the probe would catch it.

**This probe runs in CI over every registered feature**, and a feature that
fails it cannot be added to an `AgentSpec`. A leak that gets past a human review
will not get past an equality assertion.

### The falsification checks

Two cheap controls that catch leaks the probe cannot — leaks in the *environment*
rather than in the features:

1. **Shuffled-label control.** Train on the same features with the forward
   return shuffled within each fold. A leak-free pipeline must land at
   break-even minus costs. Anything that makes money here is reading the future
   through the environment.
2. **Shifted-entry control.** Re-run the approved agent with every entry
   deliberately delayed one bar. A genuine edge degrades gracefully; a leak
   collapses. This project has the scar: a route that stamped entries one bar
   late cost **10R over 152 GBPJPY trades**, which is how I know the sensitivity
   is measurable.

Both are reported next to every validation result, pass or fail.

## 4.12 Front-end control

A new **Agents** page: create (asset, timeframe, features, reward weights,
seeds, exit head on/off), upload a dataset, train with live progress over the
existing WebSocket, read the validation report, read the distilled strategy in
plain language, approve or reject, clone to a new asset. Approved agents appear
in the Backtester's strategy list as `RL::<name>@<version>` through the normal
registry, so nothing else in the app needs to know they are different — and that
is what makes them selectable for backtests and assignable to live slots exactly
like any other strategy.

Training runs in a **separate process** behind a bounded queue, never on the API
event loop — this project has already stalled the whole API once by doing MT5
frame-building on the loop.

# W5 — Codebase bug audit

Compiled every module, ran an AST audit for the defect classes that have
actually bitten this project, read the diffs of recent changes, and probed both
live terminals and the VPS database. **Twelve findings, worst first.** Two are fixed in this revision (§0).

### 🔴 1. Group-keyed risk caps go blind after a bot restart
`backend/risk/circuit_breaker.py` — `save_state()` persists
`open_positions_by_symbol` but **not `active_groups`**; `load_state()` restores
the former and never the latter. After a restart, surviving positions are
missing from `active_groups`, so `get_open_risk()`, `get_cluster_open_risk()`
and `get_net_direction_open_risk()` all return **0**. The adoption path added
2026-10-06 restores membership and floating P&L (so profit targets work) but
sets `initial_risk = 0` and leaves `direction` empty by design, because they are
genuinely unknown — **so the risk caps stay blind, silently**, and the next
signal sizes as though nothing were open.
**Fix:** persist `active_groups` under the existing account-scoping rule and
rehydrate `initial_risk`/`direction` from the `Trade` rows on adoption.

### 🔴 2. The investor NAV has never been checked against the broker
Every `nav_snapshots` row on your VPS has `source='TRADES'`. No valuation has
ever been read from broker equity, and `/reconciliation` falls back to the
latest snapshot — so it compares investor claims against a figure derived from
the same bookings and cannot disagree with itself. **A $2,207.51 difference has
therefore never been displayed.** See §1.0. Fixed by §1.5.

### 🔴 3. The live risk config dropped 22 of 93 risk fields — FIXED
`backend/risk/live_risk_config.py` was a hand-written dict literal, so a
`RiskParams` field absent from it never reached live at all. Six of the 22 were
the whole profit-target mechanism (`max_trade_profit`, `max_monthly_profit`,
`profit_target_scopes/basis/action/is_pct`) and one was
`accounting_utc_offset_hours`, so the WAT day boundary could not reach live
either. **This is the same defect class as the 2026-09-21 UI audit** (18 risk
fields unreachable in the new screens while the engine still read them), in a
different file. Now derived from the dataclass: 93 of 93. See §0.

### 🔴 4. The live profit-target pass read the account config, not the slot's — FIXED
`bot_service._apply_profit_targets` used `slot_book.config_for(slot.slot_id)`,
which falls back to `base_config` for an unregistered slot. Registration happens
only in `_slot_engine`, inside the signal-execution branch — so a slot holding an
open position and producing no new signal read the account's
`target_profit_enabled` (`False`) and was skipped before the breaker was
consulted. Now resolves the slot explicitly. See §0.

> **Both of these are a general lesson, not two one-offs:** a hand-kept list of
> fields and a silent fallback to a parent config are the two ways a setting in
> this codebase becomes decorative. The first is now derived; the second is now
> explicit at the one call site that mattered. `SlotBook.config_for` still
> falls back silently elsewhere, and that is worth auditing — it is on the
> to-do list rather than fixed, because every other caller resolves first.

### 🟠 5. `trades` has no account column
`mt5_account` is on `User`, not `Trade`. Every historical Journal row silently
re-attributes if the connected account changes. The circuit breaker already
guards against this; the Journal does not. Fixed by §1.3.

### 🟠 6. Costs are counted as deposits
`backend/mt5/order_manager.py:499`, `backend/api/routes/dashboard.py:85` —
`getattr(d, 'type', 0) >= 2` sweeps in `CHARGE(4)`, `CORRECTION(5)`,
`BONUS(6)`, `COMMISSION(7–11)`, `INTEREST(12)`, cancellations `(13,14)`,
`DIVIDEND(15,16)` and `TAX(17)`. It feeds
`prop_firm_validator.update_equity_balance(..., net_deposits=...)`, which treats
a *fall* in that total as a withdrawal and re-baselines the drawdown high-water
mark. Measured: coincidentally `$0.00` error on FundedNext today (commission
sits on the trade deals, not as separate deals), so this is latent rather than
currently wrong. Fixed by §1.2.

### 🟠 7. The obvious fix for #6 would break FundedNext
Recorded so nobody tidies it later: `type == 2` **misses FundedNext's entire
$25,000**, which arrives as `CHARGE(4)` commented `Initial+Deposit`. Measured on

### 🟠 8. Three test harnesses share a latent data-losing race
`tests/test_investor_portal.py:52`, `tests/test_investor_admin_routes.py:63`
(and `test_investor_public.py`, now fixed). `StaticPool` + `:memory:` gives every
session **one** connection, so the outbox's post-commit delivery task commits

### 🟡 9. An HTTP endpoint runs `git` and opens pull requests
`backend/api/routes/strategy_factory.py` — `/activate/{id}` writes files under

mutation over the network — and once W3 exposes a second backend through the

never enable it on a server behind the public proxy.**

### 🟡 10. Google Fonts in the admin front end
`frontend/src/index.css:1`. Every admin page load sends your IP to Google. One
line; the other three front ends are already clean.

### 🟡 11. No age attestation while the Terms require 18+
`backend/api/routes/public.py`. The policy promise and the code disagree, which
is the worse of the two failure modes.

### 🟢 12. Five `except Exception: pass` in the backtest route
`backend/api/routes/backtest.py:1483, 1787, 1798, 2204, 2303`. Low severity —
they guard optional telemetry — but they are how the three
`NameError`/indentation defects fixed on 2026-10-06 could have stayed hidden.
Use `logger.debug(..., exc_info=True)`.

### Clean on inspection
No mutable default arguments. No `float()` on investor money (the six hits are
MT5 account floats in the trading engine, which is correct). Every MT5 call path
is bound to the single `mt5_executor`. Full suite **911 passed / 2 failed**
before this session's two fixes; both now pass, and a 123-test parity subset is
