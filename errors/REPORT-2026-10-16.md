**Can several agents train together?** Yes. `RL_MAX_AGENTS` (default 1) agents run at the same time, and up to 4 more wait in the queue. Each spreads its jobs over `RL_JOB_WORKERS` processes, which by default is the cores minus 2, divided between the agents, up to 8. The rule: **agents × job workers ≤ cores − 2**, because MT5, the live bot and the API need the rest. On a 4-core VPS that means 1 agent with 2 workers. On 8 cores, either 1 agent with 6 workers, or 2 agents with 3 each. Running 2 agents doesn't make either finish sooner; it only keeps a queue moving. Set the values in `.env`; `GET /api/rl/capacity` and the export show what the server is using.

## Bug 1: turning on the supervised director crashes every training job (CONFIRMED)

- **Where:** `backend/rl/train.py` (`train_ppo` and `train_cem`), with `backend/rl/spec.py:228`.
- **What happens:** with `director=True`, `spec.observation_width` adds 2 columns for the director's call and confidence, so the policy is built 2 inputs wider. But the training loop never fits a director. It builds `feat.Scaler()` directly and never calls `TradingEnv.fit_director`. As a result, `augment()` returns the observation matrix without the 2 extra columns, and the first matrix multiply fails.
- **Reproduced locally** on the same tiny dataset the test suite uses, 40 jobs per run:

  ```
  director=False: results=40 errors=[]
  director=True:  results=0  errors=['[RL] seed 1 fold 0 failed: matmul: ... (size 27 is different from 25)']
  ```

- **Evidence in the screenshots:** both instant failures (11:42 and 11:59) have "with a supervised direction model" in their first event line. The one run that trains (12:04) does not.
- **Impact:** the "Supervised direction model + reinforcement" option on the Agents page cannot produce an agent, in either mode.
- **Fix:** fit the director inside each trainer on the same training rows as the scaler, then pass it to every `TradingEnv` the trainer builds (training windows, evaluation and test rollouts). Saving the policy should save the director too. Add a test that runs `train_agent` with `director=True` and expects at least one result.

## Bug 2: a crashed job is reported as "the policy chose not to trade" (CONFIRMED)

- **Where:** `backend/rl/train.py:681-684`.
- **What happens:** when a job throws an exception, the code logs it to the backend log and moves on. It is never added to `progress.event`, and it never reaches `run.error`. So 50 crashes out of 50 jobs show up as "Finished with no usable result" plus the warning "the policy learned to stay flat... raise iterations". That advice is wrong: raising iterations changes nothing.
- **The JSON confirms it:** `results: []`, `error: ""`, `elapsed_s: 11.7`. Yet `findings` says the run "either never started, never finished a single job, or its record was lost".
- **Fix:** collect the exception text for each failed job. Show the first one as an event (for example "seed 1 path 0 crashed: matmul ..."). If every job failed, set `run.error = "all N jobs failed: <first error>"` and turn off the "learned to stay flat" warning.

## Bug 3: mode-B agents never see their base strategy's setups (CONFIRMED)

- **Where:** `backend/rl/train.py:614`: `E.EpisodeData.build(symbol, spec.timeframe, frame, spec.features)`.
- **What happens:** neither `base_strategy=` nor `config=` is passed in. `EpisodeData.build` only calls `base_signals.generate` when `base_strategy` is set, so it is skipped and `base_signals` is always `{}`.
- **This explains the red warning** on the Data tab: "A symbol produced no DriftJumpAlpha_v1 signals at all". It appeared for Crash 1000 Index, Vol over Crash 750 and Vol over Crash 550, over both 16,631 and 99,862 bars. DriftJumpAlpha_v1 does trade those markets in the app. The training loop just never asked it for signals.
- **Impact:** every mode-B agent ("Improve an existing strategy") has nothing to choose from, so it can never take a trade.
- **Fix:** pass `base_strategy=spec.base_strategy`, the strategy's saved slot config, and the HTF frames into `EpisodeData.build` in `train_agent`. The validation gate already does this at `validate.py:589`, so it is the model to copy. Add a test that a mode-B `train_agent` run reports `base_signals > 0`.

## Bug 5: both log files are stuck failing to rotate (CONFIRMED from the console; cause traced in code)

- **What the console shows:** an endless stream of `--- Logging error in Loguru Handler #2/#3 ---` followed by `PermissionError: [WinError 32] ... logs\trades.log -> trades.2026-09-22_12-57-06_892220.log`. The same error appears for `backend.log -> backend.2026-10-16_13-25-47_156631.log`.
- **Cause:** `backend/utils/logger.py` adds the file sinks with `rotation=` when the module is imported. The training worker is a spawned process (`SpawnProcess-1`, pid 3084), so it imports the module again and opens its own handles on the **same** `backend.log` and `trades.log`. On Windows, a file another process has open cannot be renamed. So once either file reaches its size limit, every later write in either process tries to rotate, fails and prints a traceback.
- **The 2026-09-22 timestamp** means `trades.log` has been stuck since 22 Sep. It is growing without limit and its retention never runs.
- **Impact:**
  - Each log line costs a traceback, which slows training (finding 4).
  - The pm2 logs are unreadable.
  - Disk use grows.
  - It is the same writer path that caused the earlier error-sink deadlock ([[algoedge-error-sink-deadlock]]).
- **Fix:** have only the API process own the rotating file sinks. In the training and backtest worker processes, either write to a per-process file such as `logs/worker-<pid>.log`, or keep only stderr at WARNING. Detect this with `multiprocessing.current_process().name != "MainProcess"`, or an env var set by the worker's initializer. A one-off cleanup is also needed on the VPS: stop pm2, rename the oversized `trades.log`, then start pm2 again.

### Video 1: platforms, data and an MT5 bridge
- **What this project has measured:** Deriv's WebSocket API gives tick history for synthetics, MT5 gives bars and depth, and an MT5 terminal caps history (item 3 above). For real CFDs, the bars that count for backtesting are **your broker's own**, because spreads, sessions and synthetic prices differ between feeds ([[algoedge-combined-book-and-feed-problem]]: one book made t +3.76 on Deriv and -8.2% on FundedNext).
- TradingView, thinkorswim and Bookmap are research and visualisation tools. Exporting their data to backtest against and then executing through MT5 at a different broker brings back the feed mismatch.
- **Recommended setup:** backtest on the execution broker's MT5 history, which the app already does. Use Bookmap or a futures depth feed only as a *filter* input.
- If the project ever trades futures (CME micro contracts), the clean pipeline is Rithmic or CQG data plus a Tradovate or NinjaTrader API. That replaces MT5; it does not bridge into it.

### Video 2: strategies to backtest
- **Can be backtested now, on this app's MT5 data:** 15-minute ORB, the volume breakout, news fade/breakout (with the event calendar), and stop-run reversals.
  - Prior results: ORB 60m GBPJPY London 1:3 was the only ORB variant that held in all three walk-forward periods. Gold and indices did not ([[algoedge-orb-walkforward-result]]).

### Video 3: Navinder Sarao, spoofing and market making
*(The full plan, with live spread and latency measurements and what you need to provide: `research/market-making/PLAN-2026-10-16.md`.)*
- **Spoofing and layering** means placing orders you intend to cancel in order to move the price. It is a crime: Dodd-Frank §747 in the US and the Market Abuse Regulation in the UK and EU. Sarao was convicted for it. Exchanges now detect it automatically from order-to-trade ratios and cancel patterns. It is not viable, and I won't design it.
- **The legitimate version is market making:** quoting both sides and earning the spread while managing the risk of holding inventory. It is not feasible from MT5 on a CFD broker. There you are the broker's counterparty and cannot post resting orders on the real order book.
- Real market making needs:
  - exchange membership or a direct-access broker;
  - colocation or a sub-millisecond link;
  - a feed of individual orders (ITCH, MBO);
  - inventory models such as Avellaneda–Stoikov, plus models of where you sit in the order queue and of adverse selection.
- The spreads available to latecomers are thin. In crypto, maker rebates on CEX/DEX perpetuals are the realistic entry point for a small operator, but it is a separate business, not a strategy for this app.
